# 异步状态、恢复与消息选择

| 场景 | 关键选择及遗漏影响 | 验证方法 |
| --- | --- | --- |
| 页面获取数据 | 区分尚未请求、加载、有效空集合、过滤无结果、失败和已显示数据的后台刷新。骨架只在结构可预期时用，未知进度不能假造百分比；不要因刷新把可用旧数据无条件清空 | 慢请求、空结果、不同查询条件、刷新失败；确认旧请求不会覆盖新条件，读到缓存时可解释其时效 |
| 请求失败与恢复 | 可靠地区分可识别的离线、超时、认证失败、业务拒绝；不能把所有 fetch 异常断言为无网络。保留用户输入，按操作语义决定重试、重新登录或查看状态 | 隔离环境断网/超时/服务端错误；验证重试不会重复执行不可重试副作用，重新尝试后错误状态正确清除 |
| 表单或局部错误 | 与字段关联就地反馈，必要时给整体摘要并帮助定位；重要错误不能只出现两秒 | 错误文本、关联语义、键盘定位和再次提交；确认用户能在填写后仍了解字段名称与规则 |
| 非阻塞结果通知 | 普通结果用轻量消息或状态区，持续时间按长度、重要性和恢复需要决定；关键信息保留在页面中，必要的状态通知可用适当 live region | 不抢焦点；实际验证读屏通知不过度重复，用户来得及读取或能回看。不能把所有消息都设成 alert |
| 必须当下决策 | 仅在需要阻止继续当前流程时用模态；一次决策清晰，按钮写实际动作。确认方式与破坏性/可撤销性匹配 | 打开后焦点进入，Tab/Shift+Tab 保持在模态内，关闭通常恢复到触发点；测试 Escape、取消和确认的实际数据结果。不能只加 aria-modal 而让背景仍可操作 |

不把固定 1 秒骨架屏、3 秒进度文案、2 秒 Toast 或特定错误文案字数变成通用要求。模态不是所有错误的默认容器；通知方式取决于信息与任务的关系，而非只按“告知/选择”二分。

核验于 2026-10-24：[WAI 表单通知](https://www.w3.org/WAI/tutorials/forms/notifications/)、[APG 模态对话框](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)。APG 是交互模式参考，仍需结合实现与设备验证。

## 等待阶段与可计算进度

按内容结构是否已知、进度是否能可靠计算选择反馈，不按固定秒数强制套组件。按压反馈只表示收到输入；提交中表示仍在执行；业务成功需以实际结果为准。上传字节传完不代表服务端处理和保存完成，必要时分别表达阶段。未知总量不用虚构百分比或剩余时间。

对长时任务按业务选择取消、后台继续或查询结果；最终响应丢失时不能只因超时重发有副作用操作。按钮禁用用于减少重复操作，服务端仍需按请求语义保障结果。禁用原因放在用户能发现并理解的位置，不只放在无法聚焦的按钮悬浮提示里。

验证短等待是否闪烁、长等待是否可理解、进度与阶段是否一致、失败后输入和重试是否恢复。未测量时不声称满足 100ms 或固定成功率。
