# Web 请求功能的开发检查与项目拆解

以目标项目的功能为起点选择知识点。先读取相关需求、代码、请求配置和已有验证记录，区分页面导航、API 调用、静态资源及纯本地交互。没有项目材料时只输出候选检查点与所需证据，不声称项目已有缺陷或使用某项技术。

## 开发与评审

从 [references/checkpoints.md](references/checkpoints.md) 选择与当前功能有关的条目；每条关联到具体实现位置或缺失的输入，并明确：

- 触发条件：当前功能为什么需要考虑它。
- 决策与遗漏影响：需要做什么选择，忽略后具体影响哪项行为。
- 验证：通过哪段代码、配置、请求记录或测试判断已落实。

涉及接口方法、重复提交、自动重试或错误响应时，再读取 [references/http-semantics.md](references/http-semantics.md)。仅检查链路性能时无需加载这些细节。

新增或修改 API 契约、分页、Webhook，或定位慢接口时，读取 [references/api-contract.md](references/api-contract.md)，将检查关联到实际调用方和观测证据。

验收具体后端接口改动，尤其涉及失败分支、外部依赖、写入或生成测试时，按需读取 [references/backend-acceptance.md](references/backend-acceptance.md)，以业务预期和实际副作用为依据，避免只验证成功响应。

按用户目标、失败影响和实施成本确定优先级，区分当前必需、条件满足时需要及暂不适用。直接实现已授权范围内的修复；不要为展示知识而重写协议层、引入缓存设施、迁移 HTTP 版本或扩展成全项目审计。无实际请求的本地原型不强制做网络专项检查。

## 项目阐述与拆解

围绕真实核心功能建立“用户动作 → 请求/数据流 → 模块职责 → 关键决策 → 验证结果”的对应关系。每项说明解决什么问题、为何选择此实现、有什么代价，以及代码或观测依据。协议是基础机制，只有项目中确实做过的设计与实现才列为项目成果。

将已实现、计划中和待验证分开；没有数据不编造性能收益。缺少关键上下文时优先检查现有材料，仅对影响结论的缺口询问用户。篇幅随功能复杂度调整，不必机械输出所有阶段。

## 完成检查

检查点应能影响实现或验证，不能停留在缩写释义。请求成功、响应内容正确、界面显示和可交互是不同的验收结果。缓存、连接复用与 HTTP/3 会改变传统六步模型，不把每次请求都独立 DNS/TCP/TLS 当作前提。

参考文件区分视频选题、文档事实与工程应用建议。此技能已做结构与引用检查，尚未在真实开发项目中验证。
