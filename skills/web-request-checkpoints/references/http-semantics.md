# API 方法与响应处理

选择与当前接口有关的条目，并核对实际服务端契约及请求封装。

| 使用场景 | 关键选择和易漏项 | 验证依据 |
| --- | --- | --- |
| 定义读取或写入接口 | 方法要符合真实副作用，不用 GET 触发预期的业务写入；PUT 的替换语义与 PATCH 的局部修改不能混用 | 契约、处理函数和代表性请求 |
| 写入超时或用户重复操作 | 先判断首次请求是否可能已生效、重复操作是否有额外副作用；不保证幂等的请求不能盲目自动重试 | 故障注入下的最终业务状态、现有去重/条件写入契约；不要只看客户端报错 |
| 处理成功与缓存响应 | 204 没有响应内容；304 用于条件请求的缓存验证，不能一律解析 JSON 或当作普通跳转 | 覆盖实际接口约定的状态、正文缺失和缓存路径 |
| 处理失败分支 | 认证、禁止访问、找不到、限流和暂时不可用按实际契约区分；不能对所有 4xx/5xx 使用同一重试行为 | 状态映射、用户可恢复操作、重试边界及服务端提示 |

PATCH **不天然保证幂等**。例如“把字段设为指定值”和“把计数增加一次”不能仅因都用 PATCH 就视为有相同重试性质。幂等讨论的是预期效果，不能要求每次响应状态或内容相同。依据：[RFC 5789 §2](https://www.rfc-editor.org/rfc/rfc5789.html#section-2)、[RFC 9110 §9、§15](https://www.rfc-editor.org/rfc/rfc9110.html)。具体业务的去重设计是工程应用建议，须以实际实现验证。
