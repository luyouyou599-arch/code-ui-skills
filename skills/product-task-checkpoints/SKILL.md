# 产品任务与验收约定

先读取目标项目需求、现有流程、相关角色和可用证据。定位本次功能的任务边界，不因任务是 B 端或 C 端就推定商业模式、使用频率、用户规模或设计风格。需求已明确时直接应用，不重复组织产品规划。

按实际缺口补齐以下约定：

| 决策 | 易漏项 | 验证证据 |
| --- | --- | --- |
| 谁使用、谁决定采购/启用、谁承担错误后果 | 使用者与决策者可能不同；同一产品也可能兼有个人与组织场景 | 需求或实际流程中的角色、权限、上下游接收者；未知部分标待确认，不能凭行业标签填空 |
| 用户在什么情境完成什么任务 | 把“页面好看”“加一个按钮”当成目标；忽略入口、前置数据、完成后的去向 | 从入口走到可观察的结果；以真实内容核对中断和恢复，不以页面数量判断任务完成 |
| 哪些规则决定允许、拒绝和生效 | 界面显示成功但保存未完成；把前端限制当服务端约束 | 形成少量“前提 → 动作 → 预期结果及副作用”的验收场景；需要服务端执行的规则落实到实际接口和数据 |
| 用什么判断做得好 | 只验视觉还原；把点击率、使用时长或短路径自动视为更好 | 按任务选完成率、耗时、错误/返工、可理解性等相关证据，并明确对象、起止点和失败含义；没有测量就不声称提升 |

当功能目标是提高效率，尤其引入 AI 或其他自动化时，先记录现有流程的瓶颈、耗时/错误/人工接管基线，再判断规则、检索或自动化是否解决这个瓶颈，不把接入模型本身作为收益。先验证最小的端到端任务；涉及写入时另定义可接受错误、人工接管条件与副作用边界。

验收样本应覆盖当前任务的正常、模糊输入、资料缺失、拒绝及失败情况，分别观察业务结果、拒绝是否恰当、延迟与成本；不要只展示成功例或用统一平均分掩盖关键失败。样本数量由风险与覆盖缺口决定，不能把练习用的 50 条当生产验收门槛。比较改动前后时固定任务口径并记录条件差异；诊断资料、输入/提示、调用工具与业务规则分别出了什么问题，再决定改哪里。

只对影响当前决策的关键未知询问。没有用户研究材料时，可以提出待验证假设及低成本验证方法，不编造受访者、行为数据或商业结论。不要为每个小改动生成完整 PRD 或埋点体系。

将产物保持为能指导开发的简短功能约定：角色与情境、成功结果、关键规则、异常/恢复、验收证据。产品决定有效行为，交互负责操作和反馈，视觉负责表达；同一结果可能同时涉及前后端。需要具体实现检查时，再使用项目已安装且匹配的交互、视觉、请求或权限技能，不要求这些技能作为本技能运行的前置依赖。

拆解项目时，用真实需求、界面、接口或测试说明“任务 → 规则 → 实现位置 → 取舍 → 证据”；区分既有成果、改进建议和待验证假设。
