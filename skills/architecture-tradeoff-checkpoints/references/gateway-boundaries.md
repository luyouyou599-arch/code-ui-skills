# 请求入口的职责与代价

开发新增入口或拆解项目链路时，先画出实际的客户端、入口、上游服务与实例，不因名称相似就增加组件。

| 当前需要解决的问题 | 选择与易漏项 | 验证方法 |
| --- | --- | --- |
| 请求分到多个实例 | 选择符合流量与会话条件的分配和健康策略，明确故障实例如何退出 | 检查实际路由与测试环境实例故障，不只看平均分配比例 |
| 多个业务服务共用入口 | 明确路径/版本路由、转换及 TLS 终止由谁负责，避免多个位置重复或互相冲突 | 对照入口配置与上游收到的路径、头和协议，覆盖错误路由 |
| 统一身份校验 | 确认可信身份如何传递，以及资源级权限在哪验证 | 验证直达上游或伪造身份字段不会绕过实际权限边界；在授权测试环境进行 |
| 限流或保护上游 | 明确按用户/租户/地址等何种维度计数、跨实例范围和恢复提示；超时/重试需符合业务副作用 | 检查配置与临界/并发场景，避免多个层级重试使请求放大 |
| 入口自身成为依赖 | 评估容量、配置发布、观测与故障恢复成本 | 核对项目实际可用性需求和故障记录，不默认已有高可用 |

反向代理、负载均衡和 API 网关是可重叠的职责集合，单一产品可能承担多个角色。此表是工程应用判断，不能仅凭产品名称推断其配置行为。

依据（2026-10-24）：[Microsoft Gateway Routing](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-routing) 说明同一入口到不同服务/实例/版本的路由；权限与请求副作用继续按实际协议和服务实现核验。
