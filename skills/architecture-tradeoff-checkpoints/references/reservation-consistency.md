# 库存、名额与跨存储写入

适用于具体库存/名额功能，不要求系统使用 Redis。先确认业务不变量、实际吞吐、数据归属、允许的暂时不一致和恢复目标。

| 场景 | 关键选择与遗漏影响 | 验证方法 |
| --- | --- | --- |
| 检查余额/库存后扣减 | 分离的读取与写入可能竞争；按实际数据库选择带条件的原子更新、锁或版本冲突处理。检查影响行数及完整业务结果 | 隔离数据中并发争夺最后一份，确认成功数和剩余量；再检查失败路径与订单记录一致，而非只看一个数未负 |
| 多次请求同一购买 | 原子扣减不自动识别同一业务重试；明确请求标识、去重持久性和结果查询 | 相同业务请求重复/并发及客户端超时后重试，检查没有重复扣减、重复建单；不同请求不能被误去重 |
| 采用 Redis 预留 | 初始化的版本/时机、库存权威来源和可修改范围需明确；Lua 的原子执行只覆盖 Redis 端执行，不构成 Redis 与数据库的共同事务 | 验证活动重复初始化、键过期/丢失、成功扣减后进程失败、建单失败和重试；明确预留过期、补偿或对账行为 |
| 异步落库或活动结束回写 | 接收成功、预留成功和订单持久化成功是不同状态；最终回写不能单独证明过程不丢失 | 对照持久化事件/订单与预留记录，演练重复处理和中断恢复；明确未完成请求如何给用户查证 |

数据库可承受时，优先评估较简单的单库方案；高并发方案要用压测和失败结果论证收益。不能把视频“十万请求”示例当作目标项目容量证据。条件更新示例需适配目标隔离级别、索引和事务边界；序列化失败等重试也要覆盖整个正确事务范围。
