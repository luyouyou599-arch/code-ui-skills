# 核心功能的架构取舍检查

从一个具体功能或明确的架构问题开始，读取需求、实际调用与数据路径、部署边界及已有指标。区分事实、约束、假设和待验证事项。缺少量化需求时不要猜测规模或承诺性能。

按 [references/decisions.md](references/decisions.md) 选择有关取舍。涉及网关、反向代理、负载均衡或入口限流时，按需读取 [references/gateway-boundaries.md](references/gateway-boundaries.md)。涉及库存/名额预留、Redis 与数据库协作写入时，读取 [references/reservation-consistency.md](references/reservation-consistency.md)。比较当前方案与一个可行替代：需要解决什么问题、采用条件是否成立、增加了哪些状态/依赖/运维成本、怎样验证值得采用。技术名词不能代替需求。

开发时只落实已授权范围内且有理由的改动；不要为了补齐概念图加入微服务、消息队列、缓存或分片。先考虑现有结构中成本更小的解决办法。

拆解项目时，沿核心功能实际流经的组件说明各自职责、数据归属、失败路径及关键取舍。将已实现、计划中和建议分开；没有代码或部署依据时不要声称存在组件，没有测量不编造收益。

输出随任务规模调整，可以是一张功能—机制—选择理由—代价—证据的对应表。若只是单个功能的实现问题，不扩展为全系统架构审计。
