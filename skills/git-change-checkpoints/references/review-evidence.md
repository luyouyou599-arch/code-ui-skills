# 评审证据与修复收敛

在提交评审、处理发现或设计评审流程时使用；先读项目规范和实际 diff，风险依据影响与可逆性判断，不按代码是否由 AI 生成决定。

1. 将关键失败模式映射到适当证据：逻辑断言、接口副作用、构建输出或 UI 实际交互。评审意见给具体位置、触发条件与影响，区分本次引入、原已存在、待核实及偏好；不能为消除意见改掉正确行为。
2. 修复后复查新差异及必要相邻影响，去重已解决发现；同类问题检查相关实例，避免一次一行反复循环。若多轮反复或意见互相冲突，回到需求、失败证据与方案，不机械追求固定轮数或无限自动改写。
3. 项目要求的人工审批保留；自动评审通过不占用人工席位。审批与所覆盖提交对应，新改动按项目规则重新确认；不因本参考自动修改仓库保护规则。
4. 若维护评审器，使用已确认缺陷和已知正常差异同时评估漏报、误报及有害修改，并观察重复发现与收敛成本；不能只追求评论数。

交付验证输出、未覆盖项和回退边界；未运行检查不写通过。项目拆解说明真实检查如何拦截哪类失败、仍会遗漏什么，不能将工具品牌或团队统计当项目成果。
